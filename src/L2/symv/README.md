# symv — symmetric and Hermitian matrix–vector multiplication

$$y \leftarrow \alpha A x + \beta y,$$

$A$ an $n \times n$ symmetric (or Hermitian) matrix with one triangle
stored; the other triangle is read by reflection. Four routines:
`dsymv`, `ssymv` (symmetric), `zhemv`, `chemv` (Hermitian: the
reflected element is conjugated and the stored diagonal's imaginary
part is ignored, per the storage convention).

```text
dsymv(uplo, n, alpha, a, lda, x, beta, y)
```

## What the result is, exactly

This is the one Level 2 family whose result is **not** locked to the
plain definition's rounding order. The fused pass below accumulates
each column's reflected contribution in its own register and folds it
at the end, a different (equally valid) sequence from the
column-by-column sum. The contract is therefore an error bound against
a higher-precision reference, plus the usual cross-target
bit-identity (native and wasm agree bit for bit through the lane
emulation, as everywhere). The Hermitian forms treat the stored
diagonal as real; the tests poison its imaginary part to prove it is
never read.

## How it is computed

**The fused pass.** The plain definition streams each stored column
twice: once as an `axpy` for the stored triangle's contribution to
$y$, once as a `dot` with $x$ for the reflected triangle's
contribution to the diagonal element's row. The fused kernel
(`daxpy_dot` in `src/kernels.rs`) does both from one read of the
column, and its four-column form (`daxpy_dot4`) serves four columns
from one pass over $x$ and $y$, since $y$ is only ever accumulated
into and $x$ and $A$ only read, so the grouping is free of
dependencies. The ragged edge and the diagonals run scalar per column.

**Per type, the measured choice.** f64 and f32 ship the four-column
fused pass. c64 (`zhemv`) ships the four-column pass too
(`zaxpy_dotc4`): it won its race against the single-column pass on
both runner draws, 9–13% in wall time. c32 (`chemv`) ships the
single-column pass (`caxpy_dotc`): the same grouping lost its race
there by about 2% on both draws, because at two complexes per
register the extra blend work costs more than the saved traffic.
Each type ships its own winner; the loser is recorded, not exported.

The complex symmetric (unconjugated) matrix–vector product that the
Level 3 `zsymm`/`csymm` need has no reference routine and lives as a
crate-private kernel (`zaxpy_dotu`, `zaxpy_dotu4`) in this folder's
Level 3 consumer, not here.

## Performance

n = 2048, percentage of the fastest same-run memory stream, two runner
draws (the Level 2 README has the whole table and its provenance):
symv f64 53–54%, f32 48%; hemv c64 16–21%, c32 12%. The complex rows
are the lowest on the level: the fused complex pass carries the lane
product form's shuffles on both the `axpy` and the `dot` half, and the
c32 grouping lost its race. These are also what bounds the Level 3
`hemm` left side, which rides this kernel.

**What is left.** The complex hemv rows are the recorded lever; the
Level 3 cure (packing the symmetric matrix and running the gemm tile)
does not apply to a matrix–vector product, which is memory-bound. A
re-race of the c32 grouping is warranted only if the lane product
form changes.

## Tests

`tests/L2/dsymv.rs`, `ssymv.rs`, `zhemv.rs`, `chemv.rs`: error bounds
against a higher-precision reference for both triangles, the
Hermitian diagonal's imaginary part poisoned to prove it is ignored;
`semantics.rs` for $\alpha = 0$ and $\beta = 0$; `errors.rs` for the
argument checks.
